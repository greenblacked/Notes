This note is a template policy for teams whose engineers write code with AI assistants. It is written for senior DevOps engineers and engineering managers who must decide what is allowed, how it is reviewed and what can be shown to an auditor. It does not cover how to secure the agents themselves ([[ai/securing-ai-agents-in-ci-and-cloud]]) or the general review practice ([[standards/code-review]]).

> [!warning] Not legal or audit advice
> This is general engineering guidance. Your auditor, assessor or legal counsel decides what satisfies a control or a legal obligation; check control numbers and wording against the current edition of the framework.

> [!info] Scope and sources
> Written for teams using GitLab or GitHub merge requests with approval rules. It draws on common change-management practice and the SLSA and software supply-chain material at https://slsa.dev. No product is assumed.

> [!note] Not verified
> The claims below were written from documentation knowledge and were not checked against a running system or the current docs: whether SLSA or any other standard defines metadata for AI provenance (this note assumes none does), the legal status and ownership of generated code (counsel decides), and the GitLab API fields used in the example check. Check them before relying on them.

## Principles

1. **The human author owns the change.** An AI assistant is a tool. The engineer who commits or opens the merge request is responsible for its correctness, security and licence status, as with any code copied from elsewhere.
2. **Review does not get weaker because a machine wrote the code.** If anything it gets stricter, because generated code is often plausible and wrong in subtle ways.
3. **Evidence over declarations.** Rely on approvals, test results and pipeline records, which exist anyway, rather than on a statement that code is or is not AI-assisted.
4. **Proportional recording.** Record provenance where the organisation needs it, and no further.

## Rules

Put the policy in one place and link it from the contribution guide. [The owner's AI skills catalogue](https://ai.szolotov.com) holds reusable skills and workflows that teams can adapt, but a policy is only useful if the team agrees the wording itself.

- The person who submits the change is the author of record and answers for it.
- No self-approval: an agent or assistant never approves a change, and the same agent that wrote code does not provide its only review.
- At least one human reviewer who did not author the change approves, as for any change.
- Tests are not accepted as evidence if they were generated by the same agent in the same session as the code they test and never read by a human. A human reads the tests; for risky code a human writes or changes at least one test.
- Do not paste secrets, customer data or personal data into an assistant. Allowed data classes follow [[ai/securing-ai-agents-in-ci-and-cloud]].
- Generated code that adds a dependency goes through the normal dependency and licence checks ([[compliance/open-source-license-compliance]]).
- Generated code passes the same pipeline gates as any code: tests, SonarQube quality gate, secret scanning and policy checks.
- Infrastructure and security-sensitive changes (IAM, network, admission policy, pipeline definitions) get an extra reviewer from the owning team, whoever wrote them.
- Teams may forbid assistants for named areas, such as cryptography or access-control code, and write the exceptions down.

## Provenance options

Provenance means recording that a change was written or assisted by an AI tool. There is no standard format for it, and this note assumes none is defined by SLSA or similar frameworks. Choose per repository.

| Option              | What it records                                  | Trust level                                | Effort                       | Public exposure                                   |
| ------------------- | ------------------------------------------------ | ------------------------------------------ | ---------------------------- | ------------------------------------------------- |
| None                | Nothing; review and tests carry the assurance    | n/a                                        | None                         | None                                              |
| Commit trailer      | A line such as `Assisted-by:` in the commit body | Low: self-declared, easy to forget or fake | Low                          | Visible in the git history of public repositories |
| Merge request label | A label such as `ai-assisted` set by the author  | Low to medium: enforceable by a CI check   | Low                          | Visible to project members, not in git history    |
| Generation-time log | Tool-side log of prompts and outputs per session | Medium: produced by the tool, not the dev  | High; needs retention policy | Private, but may hold sensitive prompts and code  |

Some organisations forbid any tool attribution in public repositories, for example in commit messages and pull request text. That is a legitimate choice. In that case use the label or the internal log, and keep the attribution out of anything published. Decide per repository and write the choice in its contribution guide.

Whatever you pick, treat it as a convention, not as proof. A trailer shows what the author said, not what happened.

## Review requirements

- Use the same approval rules for AI-assisted and manual changes. Do not create a lighter path.
- For a merge request labelled `ai-assisted`, require at least one approval from a human who is not the author (the example check below enforces this).
- Reviewers check the things generated code tends to get wrong: invented APIs or flags, outdated syntax, missing error handling, insecure defaults, copied licence headers and silently dropped edge cases.
- Reviewers run or read the tests, and confirm the tests fail without the change.
- Large generated diffs are split. If a reviewer cannot hold the change in their head, it is too big to approve.

## Licence and IP questions for counsel

These are questions for legal counsel, not engineers. Write the answers into the policy.

- Who owns code produced by an assistant under your provider's terms, and does your contract say anything about indemnity?
- May generated output be committed to a public repository, and under which licence?
- Does the tool filter or flag output that matches public code, and does the contract say what happens if it does not?
- What does the provider retain or train on, and is that acceptable for each data class?
- Do customer contracts or regulations restrict the use of AI tools on their code or data?

Until counsel answers, engineers apply the existing licence process to every dependency and treat large verbatim-looking blocks of unfamiliar code as a licence risk.

## Evidence for change control

Auditors look for proof that changes were reviewed, tested and approved by someone other than the author. AI assistance does not change that evidence; the merge request, approvals and pipeline results do. See [[compliance/change-management-controls-and-pipeline-evidence]] for what to keep and [[standards/production-change-checklist]] for the production side.

What to keep for AI-assisted changes:

- the merge request with its label, approvals and reviewers;
- the pipeline run with test, quality gate and policy results;
- the policy document and its version history;
- records of exceptions (areas where assistants are forbidden or additionally reviewed);
- if you use generation-time logs, the retention rule and who may read them.

## CI check example

A commit with an optional internal-convention trailer, shown as an example only:

```text title="commit message"
fix(helm): set resource limits on the worker deployment

Adds CPU and memory limits and a PodDisruptionBudget.
Reviewed and tested by the author before submitting.

Assisted-by: ai-assistant
```

The trailer name is an internal convention example, not a standard. Use your own, or none.

The script below fails when a merge request labelled `ai-assisted` has no approval from a human other than its author. It uses only the Python standard library.

```python title="scripts/check_ai_mr_approval.py"
#!/usr/bin/env python3
"""Fail if an MR labelled ai-assisted lacks a human approval from a non-author."""
import json
import os
import sys
import urllib.error
import urllib.request

API = os.environ["CI_API_V4_URL"]  # set by GitLab CI
PROJECT_ID = os.environ["CI_PROJECT_ID"]
MR_IID = os.environ["CI_MERGE_REQUEST_IID"]
TOKEN = os.environ["POLICY_CHECK_TOKEN"]  # masked read_api token, no write scope
LABEL = os.environ.get("AI_LABEL", "ai-assisted")
MIN_HUMAN_APPROVALS = int(os.environ.get("MIN_HUMAN_APPROVALS", "1"))


def get(path):
    request = urllib.request.Request(
        f"{API}/projects/{PROJECT_ID}/merge_requests/{MR_IID}{path}",
        headers={"PRIVATE-TOKEN": TOKEN},
    )
    with urllib.request.urlopen(request, timeout=30) as response:
        return json.load(response)


def main():
    try:
        mr = get("")
        approvals = get("/approvals")  # field names below: check against your GitLab version
    except urllib.error.URLError as error:
        print(f"cannot reach the GitLab API: {error}", file=sys.stderr)
        return 2

    if LABEL not in mr.get("labels", []):
        print(f"MR is not labelled {LABEL}; nothing to check")
        return 0

    author_id = mr["author"]["id"]
    human_approvers = [
        entry["user"]["username"]
        for entry in approvals.get("approved_by", [])
        if entry["user"]["id"] != author_id and not entry["user"].get("bot", False)
    ]

    if len(human_approvers) < MIN_HUMAN_APPROVALS:
        print(
            f"MR labelled {LABEL} needs {MIN_HUMAN_APPROVALS} approval(s) from a human "
            f"who is not the author; found {len(human_approvers)}",
            file=sys.stderr,
        )
        return 1

    print(f"OK: approved by {', '.join(human_approvers)}")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

Wire it into the merge request pipeline:

```yaml title=".gitlab-ci.yml"
ai-mr-approval-check:
  stage: test
  image: python:3.12-slim # change: pin to the digest you have reviewed
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  variables:
    AI_LABEL: "ai-assisted"
    MIN_HUMAN_APPROVALS: "1"
  script:
    - python3 scripts/check_ai_mr_approval.py
```

Things to check before relying on it: the approvals endpoint and its `approved_by` field, whether the user object carries a `bot` flag on your instance, and that the check re-runs when approvals change (a pipeline does not re-run on approval by default; use the approval rules and a merge-time gate as the real control, and treat this job as an early warning). A label is also set by the author, so pair it with a team norm and spot checks.

## Checklist

```text
[ ] Policy is written, versioned and linked from the contribution guide
[ ] Author of record owns the change; no self-approval by the same agent
[ ] Human non-author approval required, same rules as manual changes
[ ] Generated tests are read by a human before they count as evidence
[ ] Provenance option chosen per repository (none, trailer, label, log)
[ ] Public repositories: attribution choice agrees with the organisation's rules
[ ] Data classes allowed in prompts are listed; secrets are excluded
[ ] Licence and IP questions sent to counsel; answers recorded
[ ] Dependency and licence checks run on generated changes
[ ] Exceptions and forbidden areas are documented
[ ] Evidence (MR, approvals, pipeline results) is retained per the change-control policy
```
