## Treat package names as untrusted input

A model may suggest a dependency that does not exist, has the wrong name, targets another language, or is a lookalike for a popular package. It may also invent an API for a real package or recommend an obsolete package based on old examples. Installing a guessed name can expose a developer or CI job to typosquatting, namespace confusion, malicious maintainer changes, or unnecessary transitive dependencies.

Do not install a package just to see whether the suggestion works. First establish that the dependency is necessary and verify its identity through the canonical registry and project documentation. A package registry entry proves that a name is published; it does not prove that the project is trustworthy, appropriate, maintained, or safe for your workload.

The safeguards here complement [[ai-generated-code-policy-and-provenance]] and existing software supply-chain controls. They are not a substitute for [[evaluating-ai-tools-for-a-platform-team]], which addresses tool selection rather than each code change's package additions.

## Verification workflow

1. **Inspect the diff.** Identify direct and transitive dependency changes, lockfile edits, install scripts, package sources, and version ranges. Ask why the package is required and whether the language's standard library or an already approved dependency can satisfy the need.
2. **Verify exact identity.** Check the canonical registry and upstream project for exact package name, ecosystem, publisher, repository, supported versions, release history, and documented API. Compare the registry's source link with the expected project; do not trust the model's URL or a search snippet alone.
3. **Check policy and provenance.** Confirm license and provenance expectations with the repository's approved-source policy. Review signing or provenance information when the ecosystem provides it, but do not treat a badge as a guarantee. Consult internal allowlists, vulnerability databases, and owner guidance.
4. **Pin and lock reproducibly.** Use the project's established version policy and lockfile. Avoid floating versions and broad ranges for critical tools. A lockfile records a resolution; it does not certify the resolved artifact as safe.
5. **Review transitive impact.** Inspect dependency tree, install hooks, native extensions, requested permissions, and network behavior. Run the ordinary vulnerability and dependency review checks. For unfamiliar or high-impact packages, ask the security or platform owner before adoption.
6. **Test the actual API.** Read the version-matched official documentation or source and add a minimal test for the intended call. Treat imports and methods generated by the model as unverified until the compiler, type checker, or tests establish that they exist.
7. **Record rationale.** The pull request should state purpose, alternatives, exact package and version, source verification, and maintenance owner. Remove a dependency if it was only added to support a discarded suggestion.

Use controlled registries or mirrors where the organization requires them. Preserve the full package coordinate—including ecosystem, scope or namespace, and version—so an approval cannot be reused for a different artifact. For new transitive trees, review the source and update strategy as well as the immediate package.

## Failure modes

Package confusion may involve a misspelling, a similarly named package from another ecosystem, an abandoned fork, or a legitimate package whose API changed. A malicious or compromised release can appear after an initial review. A package can also be genuine yet bring excessive size, license incompatibility, unsupported runtime requirements, or a new attack surface.

Do not infer safety from download counts, star counts, successful installation, AI confidence, or a clean automated scan. Automated tools can miss newly published malware and cannot decide whether a dependency is appropriate. Do not paste registry tokens into prompts or run installation scripts with production credentials. If a suspicious package was installed, stop use, preserve package and lockfile details, remove access to affected credentials as needed, and follow the organization's supply-chain incident process.

## Decision checklist

- Is the dependency necessary and approved for this repository?
- Was the exact package identity and version confirmed at the canonical registry and upstream source?
- Does the documented API match the generated import and supported runtime?
- Are provenance, license, vulnerability, install-script, and transitive risks reviewed?
- Is the resolved version reproducible and monitored for future updates?
- Are registry credentials restricted and absent from untrusted code execution?
- Is the rationale and maintenance owner recorded?

If identity is ambiguous or the package cannot be verified, do not install it. Replace it with a known dependency or ask the maintainer to clarify.
