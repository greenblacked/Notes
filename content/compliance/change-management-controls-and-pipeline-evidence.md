This note is the hub of the compliance section. It is for senior DevOps engineers who must show that production changes are authorised, reviewed, tested, traceable and reversible, and who would rather prove it from system records than from hand-written forms. It covers the mapping from control objectives to evidence and one concrete evidence record per deploy. Retention and storage are in [[compliance/audit-evidence-collection-and-retention]], role design is in [[compliance/separation-of-duties-in-deployments]], and freezes are in [[standards/change-freezes-and-maintenance-windows]].

> [!warning] Not legal or audit advice
> This is general engineering guidance. Your auditor, assessor or legal counsel decides what satisfies a control or a legal obligation; check control numbers and wording against the current edition of the framework.

> [!info] Scope and sources
> Written for GitLab CI, Argo CD and GKE as described in [[adr/0001-gitops-with-argocd]]. Based on the GitLab, Argo CD and Google Cloud documentation for merge request approvals, deployments, application history and Cloud Audit Logs. Frameworks such as SOC 2 (change-management criteria) and ISO/IEC 27001 (Annex A change management) are mentioned only in general terms; check the current edition of each.

## Objectives

Most change-management controls, whatever framework wording they use, reduce to six objectives. Write them down in plain words first, then attach evidence.

- **Authorised**: someone with the right to approve the change did so before it reached production.
- **Reviewed**: a person other than the author looked at the diff.
- **Tested**: automated checks ran on the exact commit that was deployed and passed.
- **Traceable**: you can go from a running workload back to a commit, a merge request and a pipeline, and forward again.
- **Reversible**: there is a tested way back, and the previous version is still available.
- **Emergency path**: urgent changes have a defined, logged shortcut that is reviewed afterwards.

The principle that makes this cheap: evidence generated by a system at change time beats evidence written by a person later. A merge request approval is a database row with a timestamp and a user ID. A sentence in a ticket saying "approved by Anna" is a claim.

> [!note] Not verified
> The claims below were written from documentation knowledge and were not checked against a running system or the current docs: the GitLab approvals API response fields, the default Argo CD application history limit, and any framework criterion numbers (none are cited on purpose). Check them before relying on them.

## Evidence chain

Each step of the delivery path leaves a record. The goal is that every edge in the chain is a system record, and that a single identifier (the commit SHA, then the image digest) links them.

```mermaid
flowchart LR
    C[Commit] -->|"author, SHA, signature"| MR[Merge request]
    MR -->|"approvals, discussion, diff"| A[Approval rules]
    A -->|"merge commit on main"| CI[CI pipeline]
    CI -->|"test and scan results, job logs"| ART[Image in Artifactory]
    ART -->|"image digest"| SYNC[Argo CD sync]
    SYNC -->|"sync history, revision"| K[GKE cluster]
    K -->|"Kubernetes audit log entries"| LOG[Cloud Audit Logs]
```

Two rules keep the chain honest. First, deploy by digest, not by mutable tag, so the digest in the record is what ran (see [[patterns/artifact-promotion-artifactory]]). Second, make the deploy path the only path: if people can `kubectl apply` by hand, the chain has a hole, and the cluster audit log is how you prove or disprove that (see [[adr/0001-gitops-with-argocd]]).

## Control matrix

Use a table like this as your working agreement with the auditor. Owners and retention are examples; set your own.

| Control               | Requirement in plain words                         | Evidence source                                                        | Retention                                                              | Owner               |
| --------------------- | -------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------- |
| Authorised change     | Only approved changes reach production             | Merge request approval records, protected branch settings export       | Per policy, see [[compliance/audit-evidence-collection-and-retention]] | Engineering manager |
| Independent review    | Reviewer is not the author                         | MR approvals with user IDs, approval rule configuration                | Per policy                                                             | Tech lead           |
| Tested                | Required checks passed on the deployed commit      | CI pipeline result for the merge commit, SonarQube quality gate status | Per policy                                                             | Platform team       |
| Traceable             | A running workload maps to a commit and an MR      | Evidence record per deploy, image digest, Argo CD history              | Per policy                                                             | Platform team       |
| Controlled deployment | Only the pipeline or named roles change production | Argo CD sync history, GKE Admin Activity audit logs, IAM policy export | Per policy                                                             | Platform team       |
| Reversible            | A previous version can be restored                 | Previous digest in the evidence record, rollback job logs              | Per policy                                                             | Service owner       |
| Emergency change      | Urgent changes are logged and reviewed afterwards  | Break-glass audit log entries, post-change review MR or ticket         | Per policy                                                             | Incident commander  |

Keep the matrix in the repository next to the pipeline, so a change to the process is itself a reviewed change.

## Recording an evidence record per deploy

Write one small JSON document per production deploy, from the pipeline, using data from GitLab's API rather than from the person triggering the job. Store it as a job artifact and copy it to your long-term evidence bucket.

The job below runs on the default branch after the image is built. It assumes a `build-image` job that exports `IMAGE_DIGEST` (for example through a `dotenv` report) and a masked project access token with only the `read_api` scope and the Reporter role, in the CI variable `EVIDENCE_API_TOKEN`.

```yaml title=".gitlab-ci.yml"
record-evidence:
  stage: deploy
  # change: any image that contains curl and jq, pinned by tag or digest
  image: registry.example.com/ci/tools:1.4.0
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  needs:
    - job: build-image
      artifacts: true
  variables:
    GIT_STRATEGY: none
  script:
    - |
      set -eu
      API="${CI_API_V4_URL}/projects/${CI_PROJECT_ID}"
      AUTH="PRIVATE-TOKEN: ${EVIDENCE_API_TOKEN}"
      # The merge request that introduced this commit on the default branch.
      MR_IID="$(curl --fail --silent --header "${AUTH}" "${API}/repository/commits/${CI_COMMIT_SHA}/merge_requests" | jq -r '.[0].iid')"
      if [ -z "${MR_IID}" ] || [ "${MR_IID}" = "null" ]; then
        echo "No merge request found for ${CI_COMMIT_SHA}; recording a direct push" >&2
        MR_IID=""
      fi
      AUTHOR="${GITLAB_USER_LOGIN}"
      APPROVERS="[]"
      if [ -n "${MR_IID}" ]; then
        AUTHOR="$(curl --fail --silent --header "${AUTH}" "${API}/merge_requests/${MR_IID}" | jq -r '.author.username')"
        APPROVERS="$(curl --fail --silent --header "${AUTH}" "${API}/merge_requests/${MR_IID}/approvals" | jq -c '[.approved_by[].user.username]')"
      fi
      jq -n \
        --arg sha "${CI_COMMIT_SHA}" \
        --arg mr "${MR_IID}" \
        --arg author "${AUTHOR}" \
        --argjson approvers "${APPROVERS}" \
        --arg pipeline "${CI_PIPELINE_ID}" \
        --arg pipeline_url "${CI_PIPELINE_URL}" \
        --arg digest "${IMAGE_DIGEST}" \
        --arg environment "production" \
        --arg recorded_at "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
        '{commit_sha: $sha, merge_request_iid: $mr, author: $author, approvers: $approvers,
          pipeline_id: $pipeline, pipeline_url: $pipeline_url, image_digest: $digest,
          environment: $environment, recorded_at: $recorded_at}' > evidence.json
      cat evidence.json
  artifacts:
    name: evidence-${CI_COMMIT_SHORT_SHA}
    paths:
      - evidence.json
    # change: match your evidence retention policy; see the retention note
    expire_in: 104 weeks
```

A sample record produced by that job:

```json
{
  "commit_sha": "3f2c1a9e5b7d4c6a8e0f1b2c3d4e5f60718293a4",
  "merge_request_iid": "412",
  "author": "anna",
  "approvers": ["boris"],
  "pipeline_id": "98123",
  "pipeline_url": "https://gitlab.example.com/shop/api/-/pipelines/98123",
  "image_digest": "sha256:0b1c2d3e4f5061728394a5b6c7d8e9f00112233445566778899aabbccddeeff0",
  "environment": "production",
  "recorded_at": "2026-10-17T09:41:12Z"
}
```

Validate the record before deploying, so a change without independent approval stops instead of being discovered in the audit. This policy is evaluated with `opa eval` or `conftest` against `evidence.json`.

```rego title="policy/deploy_evidence.rego"
package deploy.evidence

import rego.v1

approvers_other_than_author := {a | some a in input.approvers; a != input.author}

deny contains msg if {
	count(approvers_other_than_author) == 0
	msg := sprintf("commit %s has no approver distinct from the author %s", [input.commit_sha, input.author])
}

deny contains msg if {
	not startswith(input.image_digest, "sha256:")
	msg := "image_digest must be a sha256 digest, not a tag"
}

deny contains msg if {
	input.merge_request_iid == ""
	msg := sprintf("commit %s reached the deploy path without a merge request", [input.commit_sha])
}
```

```bash
set -euo pipefail

EVIDENCE_FILE="evidence.json"  # change: path of the record produced by the pipeline
POLICY_DIR="policy"            # change: directory with deploy_evidence.rego

# Prints violations and exits non-zero when any rule in deny matches.
conftest test --namespace deploy.evidence --policy "${POLICY_DIR}" "${EVIDENCE_FILE}"
```

The production deploy job must declare `needs: [record-evidence]` and run the conftest check first; otherwise nothing orders the deploy after the record and the policy, and the deploy can run without them.

A pipeline-side check is only as strong as the pipeline's integrity. Protect the CI configuration (protected branches, CODEOWNERS on `.gitlab-ci.yml`) so a change that disables the check is itself reviewed, and see [[compliance/separation-of-duties-in-deployments]] for the enforcement settings.

### Argo CD side of the chain

Argo CD records what it synced and when. Pull this alongside the pipeline record for the same commit.

```bash
set -euo pipefail

APP_NAME="shop-prod"      # change: your Argo CD application
ARGOCD_NAMESPACE="argocd" # change: namespace where Argo CD runs

# Deployment history as the CLI prints it (ID, date, revision).
argocd app history "${APP_NAME}"

# The same data from the Application resource, including deployedAt and revision.
kubectl --namespace "${ARGOCD_NAMESPACE}" get application "${APP_NAME}" \
  --output jsonpath='{range .status.history[*]}{.id}{"\t"}{.deployedAt}{"\t"}{.revision}{"\n"}{end}'
```

Argo CD keeps a limited number of history entries per application (the `revisionHistoryLimit` field; the default is not verified, check it). Do not treat Argo CD as the archive: copy the record to your evidence store at deploy time.

## Emergency changes and break-glass

An emergency path is a control, not an exception to controls. Define it so it still produces evidence.

- Name who can invoke it (an on-call engineer plus an incident commander, for example), and make the access time-boxed and logged. Prefer a just-in-time IAM grant to a standing admin role.
- Record why: link the incident (see [[runbooks/incident-response]]) in the commit message or MR description.
- Prefer a fast MR with one approver over a direct push. If the pipeline itself is down, use the break-glass role and accept that the cluster audit log becomes the primary evidence.
- Review afterwards within a period you set and write down (a working day or two is common). The review is an MR or ticket that links the Cloud Audit Log entries, confirms the change was reconciled back into Git, and closes the loop.
- Count emergency changes. A rising share is a process signal, not only a compliance one.

## Population and samples

Auditors usually ask for a population (all production changes in the period) and then pick a sample to test. Prepare for both.

- **Population**: a list of every deploy in the period. The evidence records in your artifact store, or the Argo CD and `gcloud logging read` output for the period, give this without manual work.
- **Sample**: for each selected change, they typically want the request or ticket, the approval, the test result, the deployment record and, where relevant, the rollback. With the evidence record you can answer from one file plus the linked MR and pipeline.
- **Completeness**: be ready to show that the population is complete, for example by reconciling Argo CD history against Cloud Audit Log writes to the cluster. This is where hand-made changes show up.
- **Exceptions**: keep a list of emergency changes and direct pushes with their post-reviews.

Ask the auditor early which format they accept; some want exports with timestamps and user IDs, not screenshots.

## Pitfalls

- **Approvals that can be self-granted.** If the author can approve their own MR or an admin can bypass rules, the evidence is weak. Check the project settings and keep an export.
- **Evidence in places that expire.** Pipeline artifacts, job logs and Argo CD history all age out. Copy what matters to the archive.
- **Mutable tags in records.** A tag in the record does not prove what ran; a digest does.
- **Records written by the deployer.** If the same job that deploys also writes the approver list from a variable it controls, the record proves nothing. Read approvals from the API with a separate read-only token.
- **Force-push rewriting history.** Protect default branches against force pushes so the commit in the record still exists.
- **Reconciliation gap.** Evidence for what the pipeline did says nothing about what people did outside it. Look at the audit logs too.
- **Over-collection.** Logs contain user emails and sometimes payloads; keep only what the control needs (see [[compliance/pci-dss-and-gdpr-for-devops-logs-and-data]]).
